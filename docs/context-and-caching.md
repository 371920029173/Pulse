# 上下文管理：为什么是压缩，不是裁剪

## 实测数据（DeepSeek，5475/7285 token 提示）

| 请求 | prompt | cache_hit | cache_miss | 命中率 |
|---|---|---|---|---|
| 首次（冷启动） | 5475 | 0 | 5475 | 0% |
| 完全相同再来一次 | 5475 | 5248 | 227 | **96%** |
| 追加到末尾 | 7285 | 5376 | 1909 | **74%** |
| **从头部裁掉一块** | 5475 | **0** | 5475 | **0%** |

复现：探针脚本是一次性的，已经在查清结论后删除（它会调 API，约 24k prompt tokens）。
上面的数字保留下来是因为结论依赖它们。

## 结论

提示缓存是**前缀缓存**：复用与上次请求**共同的最长前缀**的 KV。

- **追加** → 旧前缀完好 → 命中（新加的那块是 miss，属正常）
- **从头裁** → 序列在裁点之后立刻分叉 → 从该点起全部 miss

## 当初的问题（已修，见文末）

当时的 `Agent.windowedHistory()` 是**从头部裁剪**：累加到 32k 字符就丢掉最早的消息。
历史一超过阈值，**每一轮的开头都不同** →

> 之后每一轮缓存命中率都是 0%，即每轮都按全价付费。

这是**静默的成本缺陷**：功能正常，账单翻倍。

## 三种策略的缓存表现

| 策略 | 缓存 | 上下文 | 评价 |
|---|---|---|---|
| 只追加不设限 | 一直命中 | 无限增长 | 最终会被模型拒绝或成本失控 |
| **滑窗裁头（曾经的实现）** | 超阈值后**永久 0%** | 有界 | 最差：花了裁剪的代价还丢了缓存 |
| **压缩（冻结摘要）** | **只在压缩边界丢一次** | 有界 | 最优 |

压缩之所以对缓存友好：摘要生成后被**冻结**，之后每轮仍是在它后面追加，前缀保持稳定。
**前提是摘要必须冻结** —— 每轮重新生成摘要（无缓存地重跑）等于每轮改前缀，那才真的破坏缓存。

## 实现约束

1. **摘要冻结**：同一段被压缩的历史，摘要生成一次后写入历史，不再重算。
2. **压缩点固定**：不要在每轮重新决定"压缩到哪里"，否则边界漂移等于每轮改前缀。
3. **压缩边界之后必须仍能命中**：摘要文本一旦确定，就是一个稳定的前缀块。
4. 把 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 接进用量统计，否则这个问题**看不见**。

## 补测（2026-10-03，deepseek-flash）：工具表排在消息**之后**，所以消息里任何一处变动都要重付整张表

上面的表只回答了"追加行不行"，没有回答"改动的是消息里哪一段"。补测把这两件事分开：

| 请求（同一段 ~19.5k 字符历史） | prompt | cache_hit | 命中率 |
|---|---|---|---|
| 逐字节相同 | 9039 | 8832 | **98%** |
| **系统消息末尾多了一个块**（校准块那种） | 9068 | 3072 | **34%** |
| 同一个块，下一轮逐字节相同 | 9068 | 8832 | **97%** |

- 消息尾部**追加**两轮对话：命中不降反升（5504 → 5632）—— 追加本身是安全的，和上面的结论一致。
- 同一段消息，只把**工具表换序**：命中 5504 → 2048（丢 3456）。工具表按接口的序列化顺序排在消息**之后**，所以它既是缓存的一部分，又会被消息里任何一处改动推到 miss 桶。

结论要拆成两句才准确：

1. 追加到**末尾**是安全的；
2. 但"末尾"必须在**工具表之前** —— 消息里任何一处变动（包括最末尾）都会让排在它后面的整张工具表重新计费。

## 因此被修掉的第二处违例：校准块

`beginRun()` 每轮重算 `calibrationBlock` 并接在**系统消息末尾**。这正是本文档第三行自己写的禁令 ——「每轮重新生成摘要 = 每轮改前缀」—— 只是发生在系统提示词里，而不是压缩摘要里。

按上面的补测，这一句的代价是**每轮丢掉整条请求约 57% 的命中**（94% → 37%），而且丢的不只是这一句：断点之后的整段历史与整张工具表都按全价重算。工具表实测：33 个工具 22.1k 字符 ≈ 6.4k tokens，带会话级工具时 41 个工具 30.8k 字符 ≈ 8.9k tokens。

修法：**构造时建一次，然后冻结**（`calibrationFrozen`）。允许的唯一一次变化是"本来没证据 → 有了证据"，所以反过来说，同一会话里系统消息逐字节不变。

机械判据有两处，都可离线复现、都已做变异验证（改回去就红）：

- `scripts/cost-check.mjs` 第 5 节：同一会话两轮之间把证据整个换掉，断言系统消息逐字节不变；再断言跨工作区只有工作区路径一处不同（遮掉路径后逐字节相同，共同前缀实测 25.6k/27.5k = 93%）。
- `packages/agent-runtime/src/__tests__/prompt-cache.test.ts`：冻结、跨会话仍会带上该块、本会话领域列表变了也不动前缀、三个请求构造点发同一份系统消息。

## 每轮的账现在在 trace 里

`end` 事件原先记的是**agent 生命周期的累计值**，不是这一轮的。读起来像"这一轮花了 3.2M prompt tokens"（实测的一次会话记录），而 3.2M 是那次会话从头到尾的总和 —— 数字不只是不准，它指向了错的那一轮。

现在 `end.usage` 是本轮的：`requests`（这一轮发了几次请求）、`prompt_tokens` / `completion_tokens` / `total_tokens`、`cache_hit_tokens` / `cache_miss_tokens`。三者要一起看：同样的提示词发 120 次和一条很长的提示词是两种病，只看 tokens 分不出来；而缓存命中率掉下来不会改变这一轮**做了什么**，只会改变账单，所以不读这两个数就看不见。UI 的 RunTracePanel 已经把「N 次请求 · 缓存命中 X%」显示在收尾那一行。

## 缓存命中率正常，账单仍然是 900 万（2026-10-03）

上面全部在讲命中率，而真实的一次自评会话给出了一个命中率讲不通的数字：

| 读数（`sess_8cd40d35a3cb`） | 值 |
|---|---|
| 请求次数 | 35 |
| prompt tokens | **9,318,458** |
| cache_hit / cache_miss | 8,940,672 / 377,786（命中 **96%**） |
| 写进历史的记录 | 131 条，**964,280 字符** |
| 其中最大的一条 | 一次 `shell_wait`，**732,633 字符 = 76%** |

**命中率从来不是问题。** 96% 已经很好；问题是命中的那一份本身有 27 万 tokens 上下文，命中只是让它打折，而剩下 4% 的 miss 是正常会话整段输入的好几倍。前面几节修的是"别让缓存白丢"，这一节修的是**上下文本身凭什么长到 27 万 tokens**。

### 一条结果不是付一次，是每次请求都付

这是整件事的关键，也是前面所有讨论没有覆盖的一点：工具结果被推进 `history` 之后，**剩下的每一轮请求都会重发它**。所以一条 N 字符的结果，代价是 N × 这条结果之后还剩几次请求。732,633 字符的那一条后面还有二十来次请求 —— 一项就是 400 万 tokens 量级。

三个地方同时没有上限，缺一不可地把这件事放了过去：

1. `sandbox.maxOutputBytes` 默认 **0**（不设上限）；
2. 后台任务的缓冲上限是 **1MB**，而 `waitJob` 是**循环读取并累加**的 —— 一次 `shell_wait wait_ms=120000` 会把任务期间打印的全部内容一次交出去；
3. agent 把工具返回的字符串**原样**推进 `history`，之后再没有任何裁剪。

### 修法：一条工具结果进入上下文的预算是 16,000 字符

`packages/agent-runtime/src/tool-output.ts`，唯一调用点在 `agent.ts` 里工具结果落进 `history` 的那一刻。

- **有界**：超过预算就保留**开头 + 结尾**，省掉中间，并明写省了多少、原文多大 —— 和 `kb_query` 的 `full=true` 是同一套（截断了就说出来、并给出取回的办法）。
- **去路具体**：按工具给，`fs_read` 说 `startLine`/`endLine`，`kb_query` 说 `full=true`，`shell` 说改窄重跑。一句笼统的"结果太长"等于没说。
- **纯函数**：同样的输入永远给同样的输出。这不是风格问题 —— 每轮重算边界就是每轮改前缀，见本文档第三节。
- **不是见谁都裁**：预算内的结果逐字节原样通过。一个到处修剪正常回答的"预算"，是穿着预算外衣的数据丢失 bug，所以判据两边都钉。
- 夹在两层：sandbox 侧 `JOB_READ_CHARS = 12,000`（`shell_wait` 一次只交一段，保留**结尾**，复用已有的 `droppedBytes` 说明），agent 侧 16,000。sandbox 这边低于 agent 那边，所以模型看到的是工具自己的说明，而不是被第二层再包一次。
- **两处都设，不是重复**：推入 `history` 的那一刻设一次（这样**存下来的、UI 渲染的、发出去的**是同一份），拼请求时（`messagesForRequest()`）再设一次。后者对前者的产物是空操作，管的是**先有记录、后有规则**的那一半 —— 盘上已有的会话记录里就存着那种 732k 字符的结果，只在前者设预算，用户一恢复那条会话，账单照旧。它刻意**不**改写盘上的记录：打开一份会话不该顺手改它，它保证的是那句更窄、也更老实的话 —— **发出去的是有界的**。

实测同一批数据上的量级：200,069 字符 → 16,000 字符（8.0%），**每一个后续请求少付 ≈53,000 tokens**。

### 顺带发现：有两条请求绕过了唯一的构造点

三处请求构造里，confirm 与 patch 两条续跑路径原本是手写的 `[system, ...history]`，不走 `messagesForRequest()`。这意味着任何加在构造点上的规则（这一节的预算、以及更早的系统消息冻结）都**盖不到这两条路** —— 而"人工确认后跑的那条命令"恰恰是最容易跑很久的那种（构建、全量检查）。现在两条续跑路径改成同一个构造函数，`budgetToolResult` 也加在确认路径写回工具结果的那一处。

### 判据
