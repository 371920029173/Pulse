# 上下文管理：为什么是压缩，不是裁剪

## 实测数据（DeepSeek，5475/7285 token 提示）

| 请求 | prompt | cache_hit | cache_miss | 命中率 |
|---|---|---|---|---|
| 首次（冷启动） | 5475 | 0 | 5475 | 0% |
| 完全相同再来一次 | 5475 | 5248 | 227 | **96%** |
| 追加到末尾 | 7285 | 5376 | 1909 | **74%** |
| **从头部裁掉一块** | 5475 | **0** | 5475 | **0%** |

复现：探针脚本是一次性的，已经在查清结论后删除（它会调 API，约 24k prompt tokens）。
上面的数字保留下来是因为结论依赖它们。

## 结论

提示缓存是**前缀缓存**：复用与上次请求**共同的最长前缀**的 KV。

- **追加** → 旧前缀完好 → 命中（新加的那块是 miss，属正常）
- **从头裁** → 序列在裁点之后立刻分叉 → 从该点起全部 miss

## 当初的问题（已修，见文末）

当时的 `Agent.windowedHistory()` 是**从头部裁剪**：累加到 32k 字符就丢掉最早的消息。
历史一超过阈值，**每一轮的开头都不同** →

> 之后每一轮缓存命中率都是 0%，即每轮都按全价付费。

这是**静默的成本缺陷**：功能正常，账单翻倍。

## 三种策略的缓存表现

| 策略 | 缓存 | 上下文 | 评价 |
|---|---|---|---|
| 只追加不设限 | 一直命中 | 无限增长 | 最终会被模型拒绝或成本失控 |
| **滑窗裁头（曾经的实现）** | 超阈值后**永久 0%** | 有界 | 最差：花了裁剪的代价还丢了缓存 |
| **压缩（冻结摘要）** | **只在压缩边界丢一次** | 有界 | 最优 |

压缩之所以对缓存友好：摘要生成后被**冻结**，之后每轮仍是在它后面追加，前缀保持稳定。
**前提是摘要必须冻结** —— 每轮重新生成摘要（无缓存地重跑）等于每轮改前缀，那才真的破坏缓存。

## 实现约束

1. **摘要冻结**：同一段被压缩的历史，摘要生成一次后写入历史，不再重算。
2. **压缩点固定**：不要在每轮重新决定"压缩到哪里"，否则边界漂移等于每轮改前缀。
3. **压缩边界之后必须仍能命中**：摘要文本一旦确定，就是一个稳定的前缀块。
4. 把 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` 接进用量统计，否则这个问题**看不见**。

## 已实现，并实测通过

`messagesForRequest()` + `compaction.test.ts` 钉住一条**刻意的决定**：历史**完整发出**，
**什么都不删**。早期版本在第 120k 字符处把历史换成一页 8k 的摘要，结果是文件还在长、模型却再也

## 补测（2026-10-03，deepseek-flash）：工具表排在消息**之后**，所以消息里任何一处变动都要重付整张表

上面的表只回答了"追加行不行"，没有回答"改动的是消息里哪一段"。补测把这两件事分开：

| 请求（同一段 ~19.5k 字符历史） | prompt | cache_hit | 命中率 |
|---|---|---|---|
| 逐字节相同 | 9039 | 8832 | **98%** |
| **系统消息末尾多了一个块**（校准块那种） | 9068 | 3072 | **34%** |
| 同一个块，下一轮逐字节相同 | 9068 | 8832 | **97%** |

- 消息尾部**追加**两轮对话：命中不降反升（5504 → 5632）—— 追加本身是安全的，和上面的结论一致。
- 同一段消息，只把**工具表换序**：命中 5504 → 2048（丢 3456）。工具表按接口的序列化顺序排在消息**之后**，所以它既是缓存的一部分，又会被消息里任何一处改动推到 miss 桶。

结论要拆成两句才准确：

1. 追加到**末尾**是安全的；
2. 但"末尾"必须在**工具表之前** —— 消息里任何一处变动（包括最末尾）都会让排在它后面的整张工具表重新计费。

## 因此被修掉的第二处违例：校准块

`beginRun()` 每轮重算 `calibrationBlock` 并接在**系统消息末尾**。这正是本文档第三行自己写的禁令 ——「每轮重新生成摘要 = 每轮改前缀」—— 只是发生在系统提示词里，而不是压缩摘要里。

按上面的补测，这一句的代价是**每轮丢掉整条请求约 57% 的命中**（94% → 37%），而且丢的不只是这一句：断点之后的整段历史与整张工具表都按全价重算。工具表实测：33 个工具 22.1k 字符 ≈ 6.4k tokens，带会话级工具时 41 个工具 30.8k 字符 ≈ 8.9k tokens。

修法：**构造时建一次，然后冻结**（`calibrationFrozen`）。允许的唯一一次变化是"本来没证据 → 有了证据"，所以反过来说，同一会话里系统消息逐字节不变。

机械判据有两处，都可离线复现、都已做变异验证（改回去就红）：

- `scripts/cost-check.mjs` 第 5 节：同一会话两轮之间把证据整个换掉，断言系统消息逐字节不变；再断言跨工作区只有工作区路径一处不同（遮掉路径后逐字节相同，共同前缀实测 25.6k/27.5k = 93%）。
- `packages/agent-runtime/src/__tests__/prompt-cache.test.ts`：冻结、跨会话仍会带上该块、本会话领域列表变了也不动前缀、三个请求构造点发同一份系统消息。

## 每轮的账现在在 trace 里

`end` 事件原先记的是**agent 生命周期的累计值**，不是这一轮的。读起来像"这一轮花了 3.2M prompt tokens"（实测的一次会话记录），而 3.2M 是那次会话从头到尾的总和 —— 数字不只是不准，它指向了错的那一轮。

现在 `end.usage` 是本轮的：`requests`（这一轮发了几次请求）、`prompt_tokens` / `completion_tokens` / `total_tokens`、`cache_hit_tokens` / `cache_miss_tokens`。三者要一起看：同样的提示词发 120 次和一条很长的提示词是两种病，只看 tokens 分不出来；而缓存命中率掉下来不会改变这一轮**做了什么**，只会改变账单，所以不读这两个数就看不见。UI 的 RunTracePanel 已经把「N 次请求 · 缓存命中 X%」显示在收尾那一行。

## 缓存命中率正常，账单仍然是 900 万（2026-10-03）

上面全部在讲命中率，而真实的一次自评会话给出了一个命中率讲不通的数字：

| 读数（`sess_a1b2c3d4e5f6`） | 值 |
|---|---|
| 请求次数 | 35 |
| prompt tokens | **9,318,458** |
| cache_hit / cache_miss | 8,940,672 / 377,786（命中 **96%**） |
| 写进历史的记录 | 131 条，**964,280 字符** |
| 其中最大的一条 | 一次 `shell_wait`，**732,633 字符 = 76%** |

**命中率从来不是问题。** 96% 已经很好；问题是命中的那一份本身有 27 万 tokens 上下文，命中只是让它打折，而剩下 4% 的 miss 是正常会话整段输入的好几倍。前面几节修的是"别让缓存白丢"，这一节修的是**上下文本身凭什么长到 27 万 tokens**。

### 一条结果不是付一次，是每次请求都付

这是整件事的关键，也是前面所有讨论没有覆盖的一点：工具结果被推进 `history` 之后，**剩下的每一轮请求都会重发它**。所以一条 N 字符的结果，代价是 N × 这条结果之后还剩几次请求。732,633 字符的那一条后面还有二十来次请求 —— 一项就是 400 万 tokens 量级。

三个地方同时没有上限，缺一不可地把这件事放了过去：

1. `sandbox.maxOutputBytes` 默认 **0**（不设上限）；
2. 后台任务的缓冲上限是 **1MB**，而 `waitJob` 是**循环读取并累加**的 —— 一次 `shell_wait wait_ms=120000` 会把任务期间打印的全部内容一次交出去；
3. agent 把工具返回的字符串**原样**推进 `history`，之后再没有任何裁剪。

### 修法：一条工具结果进入上下文的预算是 16,000 字符

`packages/agent-runtime/src/tool-output.ts`，唯一调用点在 `agent.ts` 里工具结果落进 `history` 的那一刻。

- **有界**：超过预算就保留**开头 + 结尾**，省掉中间，并明写省了多少、原文多大 —— 和 `kb_query` 的 `full=true` 是同一套（截断了就说出来、并给出取回的办法）。
- **去路具体**：按工具给，`fs_read` 说 `startLine`/`endLine`，`kb_query` 说 `full=true`，`shell` 说改窄重跑。一句笼统的"结果太长"等于没说。
- **纯函数**：同样的输入永远给同样的输出。这不是风格问题 —— 每轮重算边界就是每轮改前缀，见本文档第三节。
- **不是见谁都裁**：预算内的结果逐字节原样通过。一个到处修剪正常回答的"预算"，是穿着预算外衣的数据丢失 bug，所以判据两边都钉。
- 夹在两层：sandbox 侧 `JOB_READ_CHARS = 12,000`（`shell_wait` 一次只交一段，保留**结尾**，复用已有的 `droppedBytes` 说明），agent 侧 16,000。sandbox 这边低于 agent 那边，所以模型看到的是工具自己的说明，而不是被第二层再包一次。
- **两处都设，不是重复**：推入 `history` 的那一刻设一次（这样**存下来的、UI 渲染的、发出去的**是同一份），拼请求时（`messagesForRequest()`）再设一次。后者对前者的产物是空操作，管的是**先有记录、后有规则**的那一半 —— 盘上已有的会话记录里就存着那种 732k 字符的结果，只在前者设预算，用户一恢复那条会话，账单照旧。它刻意**不**改写盘上的记录：打开一份会话不该顺手改它，它保证的是那句更窄、也更老实的话 —— **发出去的是有界的**。

实测同一批数据上的量级：200,069 字符 → 16,000 字符（8.0%），**每一个后续请求少付 ≈53,000 tokens**。

### 顺带发现：有两条请求绕过了唯一的构造点

三处请求构造里，confirm 与 patch 两条续跑路径原本是手写的 `[system, ...history]`，不走 `messagesForRequest()`。这意味着任何加在构造点上的规则（这一节的预算、以及更早的系统消息冻结）都**盖不到这两条路** —— 而"人工确认后跑的那条命令"恰恰是最容易跑很久的那种（构建、全量检查）。现在两条续跑路径改成同一个构造函数，`budgetToolResult` 也加在确认路径写回工具结果的那一处。

### 判据

- `packages/agent-runtime/src/__tests__/tool-output.test.ts`：有界、首尾是原文、数字是真的、去路分工具、纯函数、边界不触发、空结果不被"补"；外加**恢复出来的旧会话**那一组（进请求时有界、去路仍按工具、**不改盘上的记录**、对本版本写的记录是空操作且原样返回同一数组）。
- `scripts/cost-check.mjs` 第 6 节：驱动真实 Agent，断言进上下文的那一条不超预算、模型收到的和落盘的是同一份、**预算内的一条逐字节原样**；再用 `setHistory` 塞一条 732,633 字符的旧记录，断言它**进请求**时被压住、去路仍按工具、且盘上的记录没被就地改短。

## 与 Cursor 的对照：它做的是同一件事，但把"窗口被谁吃掉了"摆在你面前（2026-10-05）

Cursor 官方文档里关于上下文的全部说法（`cursor.com/docs/agent/prompting`，2026-10-05 取）：

> Every chat shares a fixed context window with the model. As you add files, run tools, and exchange
> messages, those tokens fill up. **When the window gets close to full, Cursor compresses older parts
> of the conversation into a summary** to leave more room for new conversation.

点开输入框旁边的**上下文环**，它给出一张分类账：System prompt / Tools / Rules / Skills / MCP /
Subagents / **Summarized conversation** / Conversation（你的消息、回复与工具结果）。它模型那一页
每个模型还标着 **默认窗口 / 最大窗口** 两栏（例如 200k / 1M）。

对照结论：**核心机制是同一件** —— 到顶把早期对话压成摘要（我们：阈值 0.8 的冻结摘要 + 固定压缩点）。
差别在三处，其中两处这一轮补上了：

| | Cursor | 我们（本轮之前） | 现在 |
|---|---|---|---|
| 到顶压摘要 | ✅ 文档明说 | ✅ | ✅ |
| 窗口"被谁吃掉了" | ✅ 上下文环 + 分类账 | ❌ 只有 usedTokens 一个数 | ✅ `getContextStatus().breakdown`（系统 / 工具表 / 摘要 / 工具结果 / 对话），状态行与接口都能读 |
| 压缩后的原文 | 文档未提（摘要即全部） | ❌ 摘要之外什么都取不回来 | ✅ 被折叠的那一段落盘，摘要抬头给出可读路径，模型按需 `fs_read` 取回 |
| 猜错的窗口 | 每模型两栏 + 可切 | ❌ 猜完就固定 | ✅ 被拒绝时从报文里读到真实上限，当场改、落盘、下次构造直接用 |
| 大工具结果 | 文档未细分 | ✅ 到达时 16k 字符预算 + 全文落盘 | ✅ 同前 |

### 故意没做的两件，以及为什么

- **"清理旧工具结果"（Anthropic 的 `clear_tool_uses` 那一类）。** 在我们这套里它是多余的：旧工具结果
  本来就在压缩点之前，早已随那一段进了摘要；再单独清一次只会**多改一次前缀**（多一次缓存未命中）。
  它真正有用的场景是"保留整段转写、只清工具结果就能不超窗口"的架构 —— 而我们是压缩式的。
- **界面上的上下文环。** 接口已经给出分类账（面板可以直接画），但界面新增中文文案会顶到
  `check:i18n` 的棘轮（硬编码中文数只许降）。这一层要动，得连着 i18n 基线一起决定。


## 用本仓库自己的东西再升一级（2026-10-06）

上面那三处（分类账 / 原文可回读 / 学窗口）是对照 Cursor 补的**通用做法**。这一节的两处不一样：它们从
这个仓库**自己**已有的东西里长出来 —— 每次请求的**用量账**（run trace 的 `request` 事件与 usage），
以及**词法/结构化的取回文化**（grep、fs_read、组结构 KB）。

### 1. 换算比自校准：3.47 不再靠人工重测

`CHARS_PER_TOKEN = 3.47` 是实测常量，而本文档此前写着"换模型或换分词器要人工重测"。可每次请求的
usage 里一直带着答案：我们完全知道自己发了多少字符（`pendingRequestChars`），模型报回来的
`prompt_tokens` 就是真值，两者一比就是这一次的换算比。

- 拿到 usage 就观测一次：**样本不足 3 个不动**、取**中位数**（一次异常不该把比例拉走）、夹紧 [2.5, 5.0]。
- **数量级不对的样本不算**：真实的换算比差异来自分词器与语言，量级在 ±50% 以内；差一个数量级的"样本"
  说明那个数字根本不是 prompt token（本仓库的判据脚本里就有一个固定报 100 的桩）。带偏的方向可能正是
  撞墙的那一侧，所以这条护栏比"多学一点"重要。
- 按 **模型 + 端点** 落盘到 `.she/estimate-calibration.json`（换模型不继承上一个的值），下次构造直接用。
- 它**不参与请求字节**，只影响"什么时候压" —— 和窗口那一条同理，所以随时可以改、改错了也只是早压/晚压。

### 2. 摘要带"取回锚点"：把"压过了"变成"能找回来"

上一轮已经给了原文落盘的路径，但路径只回答"去哪找"，不回答"找什么"。摘要抬头现在还列一串**原文里真的
出现过**的串：

| 类别 | 例子 | 怎么用 |
|---|---|---|
| 文件路径 | `packages/kb/src/engine.ts` | `grep` 它，或直接 `fs_read` |
| 命令的可执行名 | `pnpm` | "那次到底跑了什么"按名字找 |
| 报错与失败标记 | `Error:`、`DENIED:`、`exit code: 1` | 下一轮最常要的原文 |
| 知识库组路径 | `architecture/context` | 直接 `kb_query` 按组查 |

抽取是**确定性的**（按出现次数降序；同频次取**较晚**出现的 —— 折叠点之前的最后几条最可能被引用；最后
按字典序兜底）、**有界**（≤10 条），并且**和摘要一起冻结**（算一次写进 state，之后逐字节重发）。

**没抽出锚点时一个字都不印**：印一句"可以用这些找：（）"是在暗示有线索，而实际什么都没有。

判据：`context-ceiling.test.ts`（确定性、有界、四类都认、抬头里列出来并冻结、空的时候不印）+
`scripts/context-budget-check.mjs` 第 12 节（真 server：自校准真的动到桩报的那个数并落盘；纯文本历史
抽不出锚点 → 不印空表）。

### 三处新增的判据

- `context-ceiling.test.ts`：分类账按类别分开且合计等于这次请求、压过之后摘要那一格大于 0；
  原文路径存在且抬头里写着它、路径跟着摘要一起冻结；`windowFromOverflowError` 认得出 `maximum
  context length is N`，**不认** `max_tokens: 4096` 这种数字；学到以后当场改、落盘、换个模型不继承；
  学到之后重发次数仍然有界。
- `scripts/context-budget-check.mjs` 第 11 节（起真 server）：分类之和与 `usedTokens` 一致、摘要那一格
  大于 0、原文路径真的能读、窗口在第 10.4 节那次真实 400 之后变成报文里写的数并点名 `learned`。


## 天花板：到顶就压，不是到顶就死（2026-10-05）

用户报的问题：**上下文一到模型上限，整条会话就不可用了。**

根因不在"压不压"上，而在**没人知道窗口有多大**：`messagesForRequest()` 把整段历史原样发出，代码里
没有任何地方知道模型能吃多少 token。超过之后模型端返回 4xx，`failTurn()` 把它归成"模型端错误"并建议
"可以直接再说一次" —— 而重试必然同样失败，且历史只会更长。这条会话从此不可用。

### 为什么不靠"从头部裁"

第一节的实测已经回答了：从头裁使每轮开头都不同，命中率 96% → **0%**（每轮全价），而且模型再也看不到
早先的轮次，可用的会话长度被卡死。所以救援的每一步都在对抗这两点。

### 机制

| 环节 | 做法 | 为什么 |
|---|---|---|
| 窗口从哪来 | 设置页填的 > `SHE_CONTEXT_WINDOW` > 按模型名识别 > 保守默认 128k | 猜错的代价不对称：猜小是过早压缩，猜大是"该压不压"（有模型端那条兜底）。**来源跟着数字一起回显**，用户才可能怀疑它 |
| 什么时候压 | 请求估算 ≥ 窗口 × `context.compactAtShare`（默认 0.8）；压过一次后阈值抬到 0.95 | 0.8 留出一次工具调用的余量；不抬阈值就会压完立刻又越线，于是每轮压一次、每轮改前缀 |
| 切在哪 | 被摘要的是 `history[0..covered)`，切点**必须落在 assistant 消息上** | 摘要以 user 角色插入；切在 user 上会得到连续两条 user，请求当场不合法（Anthropic 直接透传 messages）。切在 assistant 上还保证 tool_calls 与它的结果不被切开 |
| 摘要谁写 | 优先模型，失败或短于 40 字符就退回机械提取 | 机械提取不是失败；压不动（没有合法切点、或压完没变小）才是 |
| 摘要存哪 | 冻结进 `.she/sessions/<id>/compaction.json`（原子写），每轮原样重发 | 每轮重算 = 每轮改前缀 = 每轮全价。文件用不了就挪到一边，绝不就地覆盖 |
| 盘上的记录 | **一条不动**，`historyForDisk()` 仍是完整转写 | 用户打开会话看到的、重启后恢复的，都是完整记录；压缩只改"发给模型的那一份" |
| 边界校验 | 先用记录里的 `covered` 定位，位置对不上才退回指纹匹配，且取**离记录位置最近**的一个 | 指纹是"角色 + 开头一段"，两条都以"好的"开头的 assistant 消息指纹相同 —— 从头扫会挑中更早的那条，本该折叠的一整段又进了请求 |
| 模型端拒绝 | `isContextOverflowError` 认出"太长"就当场压一次再发，最多两次（第二次留得更少） | 阈值那条线靠"我们猜的窗口"，猜大了只有模型端自己说的话能救。限流/超时/鉴权**不算**溢出：为一次 429 压上下文，是白付一次全价再加丢掉细节 |

### 实测（本次，走 dist，桩模型，40k 窗口）

| 读数 | 值 |
|---|---|
| 历史 | 24 条 / 120,160 字符 |
| 请求条数 | 25 → **5** |
| 估算 tokens | 47,373 → **15,807**（33%） |
| 被折叠 | 21 条 |
| 摘要 | 494 字符，模型写，只生成 **1 次** |
| 固定开销（每次请求都要付） | 系统提示词 20,748 字符 + 32 个工具 23,474 字符 ≈ 12.7k tokens |
| 盘上转写 | 一条不少 |

复现：`node scripts/context-measure.mjs`（本地桩模型，不发外网、不花钱）。

### 更新（2026-10-06）：厂商规格到手，表跟着改

用户给了厂商模型页：**deepseek-flash（= DeepSeek-V4.1-Flash）与 deepseek-v4-pro 的上下文长度是 1M**
（输出上限 384K；命中/未命中的输入单价也一并给了）。于是模型表里 DeepSeek 分成两条：

| 匹配 | 值 | 依据 |
|---|---|---|
| 模式 `deepseek-` 后面是 `flash` 或 `v4` | **1M** | 厂商模型页（2026-10-06） |
| 其余带 `deepseek` 的名字（chat / reasoner 等） | 128k | 早于 V4 的型号，取保守值 |

窄的写在宽的前面 —— 一条笼统的 `/deepseek/` 只能二选一，而两个方向都错得起：给老模型 1M 会"该压不压"，
给新模型 128k 会白白早压。

**同时把窗口写进配置**：`.env` 里 `SHE_CONTEXT_WINDOW=1000000`（设置页的「上下文窗口」写的是同一个键）。
这样即使换一个名字不在表里的模型，判据也是"这个端点 1M"，而不是那条保守猜测。
### 真端点上量了一次：这张表是保守的（2026-10-05）

`scripts/context-overflow-probe.mjs`（要 key，**故意不进 `check:offline`**）把一份超长提示词直接发给
真端点，看它到底在哪拒绝：

| 提示词 | 结果 |
|---|---|
| 60 万字符 ≈ 17 万 token | 接受了，正常回答 |
| 240 万字符 ≈ 69 万 token | 接受了，正常回答（5.2s） |

两件事跟着定下来：

1. **这张表对这个端点是保守的**（表里 DeepSeek 家族取 128k，实测接受 ≥692k）——保守是有意的方向：
   猜小的代价是"过早压缩"（一次缓存未命中 + 细节提前离开上下文），猜大的代价是"该压不压"。
   真知道自己的上限时，**填 `llm.contextWindow` / `SHE_CONTEXT_WINDOW` 比改代码直接**，状态行与
   设置页都会显示这个数字的来历。
2. **这个端点上没能复现出真实的溢出 4xx。** 所以"模型端说太长"那条兜底是用**带真实措辞的桩 400**
   验的（`scripts/context-budget-check.mjs` 第 10.4 节），不是用一次真拒绝验的。这一点在交付里如实
   标着 —— 一条只在桩上走过的分支，不该说成"线上验过"。

**固定开销只能算一次。** 初版把系统提示词同时算进了 `messages[0]` 和固定开销，估算因此偏大约 6k
tokens，对 40k 窗口意味着触发线整体前移 15% —— 也就是"还没到该压的时候就压了"。上面这两个数字
（12.7k / 6k）是那一轮对账量出来的，不是推理出来的。
