# 2.0：召回从「模型自愿」改成「系统默认推送」

> 2026-10-27。用户的原话：模型**不知道自己不知道什么**，所以不回查 KB；地图也很少用。

## 一句话
把"要不要查记忆"从模型的自由意志，改成系统的默认路径；模型只负责在默认路径不够用时补刀。

## 五个部件（每一个都能单独关掉）

| 部件 | 文件 | 干什么 | 关掉 |
|---|---|---|---|
**L0 目录卡** | `agent-runtime/src/kb-index-card.ts` | 系统消息里一段 ≤1400 字符的"库里有哪几组、各多少条、最近写入"。**构造时算一次**，随 `system-message.json` 冻结 | 库为空时自然为空串 |
**L2 条件锚路由** | `agent-runtime/src/recall-router.ts` | 按用户这句话判定 code / history / writing / chat，决定优先查哪几组、预算多少；**chat 直接不召回** | — |
**决策点状态行** | `agent-runtime/src/agent.ts`（`describeRecall`） | 每轮末尾一行：「本轮自动召回 N 条（原因）。id: …—— 不够就 kb_query 补查」；**0 条时明说"库里没找到"** | `SHE_KB_AUTO_RECALL=0` |
**地图推送** | `agent-runtime/src/map-impact-line.ts` | 这句话提到工作区文件时，附一行影响面（被几处引用 / 要跑哪些 check / 相关测试数） | `SHE_MAP_PUSH=0` |
**recall_when + 比例摘要** | `kb-tools.ts` / `compaction.ts` | 写入时记"什么上下文该召回它"；摘要预算 = max(窗口 1%, 原文 5%)，上限 6 万字符 | 不传 recallWhen 时降级但可用 |

## 缓存账（这是"能不能长期用"的关键）
- **前缀部分**（会破缓存的）：只有 L0 卡片，而且**一次会话不变**；
- **尾部部分**（不破缓存的）：状态行 ~40 字符、召回块 0–450 token、影响面 0 或 ~30 token、地图摘要 ~40 token；
- 也就是说：新增的全部成本都落在"追加"上，`prefix-stability` / `prompt-cache` 两条判据继续成立（32/32、36/36 实测）。

## recall_when 是什么
外部资料里最值钱的一句：**锚点不是路径，是匹配器**。所以写入时问的不是"这条属于哪个文件"，而是"什么上下文该想起它"：

```
kb_upsert({ groupName, title, content,
  recallWhen: "改 shell 调用或引号处理、Windows 命令行时" })
```

- 写得出 → 入库，`kb_query` 结果里会显示「召回条件：…」；
- 写不出 → **仍然入库**（旧记忆补不上，硬性必填只会让模型编造），但标 `noRecallWhen`，检索时靠语义兜底。

## 旧库迁移
**不需要迁移**。`recallWhen` 存在 `memories.metadata`（那一列本来就是 `TEXT '{}'`），旧节点读出来就是没有这个字段 → 按弱锚处理。想给最重要的旧记忆补条件，用 `kb_edit` 或用 `kb_upsert onExisting="update"` 重写一次即可。

## 怎么验证它真的在起作用
```bash
pnpm check:recall     # 8 条判据，离线、不花钱
```
它钉的是：卡片 ≤1400 且两次逐字节相同、正负集各 5 条（漏召回 0 / 误触发 0）、强锚 recall@3、弱锚仍可检索、空库/坏引擎返回空串。

## 2.0 里刻意没做的事
- **没有引入向量检索**（仓库规则）：召回精度靠组结构、边扩散、条件锚；
- **没有每轮全量召回**：chat 轮零召回，其余按任务类型给预算；
- **没有把摘要当历史**：`compacted/` 原文永远先落盘，摘要变大（原文 5%，上限 6 万）只是让它更接近真相。
