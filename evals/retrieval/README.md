# Retrieval evaluation / 检索评测

```
node evals/retrieval/run.mjs              # 默认用 fixture（无需真实库）
node evals/retrieval/run.mjs --db <path>  # 指定真实库（例如 <工作区>/.she/kb.sqlite）
node evals/retrieval/run.mjs --json       # 机器可读输出
```

**不调用任何 LLM API**，纯离线，毫秒级。

没有真实库时会自动退回 `fixture.json`：它是一份静态样本，复现检索的结构形态，让 CI 在没有
个人知识库的机器上也能跑。要评估真实数据就传 `--db`。

## 为什么要做这个

这个项目的核心主张是「用结构共振检索替代向量检索」。**主张在没有数字之前只是个人意见**，而任何读者第一个问题都是「为什么不直接用 BM25 / embedding？」

所以每个用例都**同时用两套系统跑同一份数据**：

| 列 | 是什么 |
|---|---|
| `hybrid` | `GroupKBEngine.query()` — 结构共振 + BM25 + 锚点 |
| `bm25` | `store.bm25Search()` — 纯词法，诚实的基线 |

**两列的差距就是证据。**

## 当前结果（本次运行：fixture 装置库，29 组 / 41 节点，60 条用例）

```
Top-1 命中    hybrid 100% (53/53)    bm25 64% (34/53)    bm25+rerank 64% (34/53)
Top-3 召回    hybrid 100% (53/53)    bm25 64% (34/53)
负例（不该命中） 14% (1/7)
```

> 这三行是 2026-10-10 的读数（60 条用例 = 53 正例 + 7 负例）。**要引用就用你自己那次** ——
> `pnpm eval` 每次都会重新打印，数字会随用例和算法变化。
```

### 增益来自哪里（重要）

+19 **全部来自「词法检索寻址不到」的那两类查询**（组路径、标题）。第三列 `bm25+rerank` 是在
**同一批候选**上做重排（标题命中 ×0.6 + 组路径命中 ×0.4 + 路径深度惩罚）—— 它**一分都没涨**：

```
Top-1 命中    hybrid 100% (53/53)    bm25 64% (34/53)    bm25+rerank 64% (34/53)
```

原因很直接：这类查询上 BM25 只返回 0–2 条候选，**答案根本不在候选集里**。重排只能改顺序，
救不了候选生成 —— 这把结论从「BM25 差一点」推到「BM25 **无法寻址**这一类查询」。

语义类用例上两者打平（都 100%）——**这一点必须承认**，不能说结构检索在语义匹配上更强。

## 用例设计

`cases.json` 分四类：

| kind | 判据 |
|---|---|
| `group` | top-1 必须**属于**该组（不是标题匹配——早期版本拿标题去匹配组路径，永远匹配不上，得出过错误的 60%） |
| `title` | top-1 必须是**那条**节点 |
| `semantic` | top-1 属于可接受组集合中的任意一个（多个组合法地覆盖同一主题） |
| `negative` | 库中完全不存在的主题，**不应**给出命中 |

## 已知局限（别当它比实际更强）

- **只有一个装置库**：60 条用例都跑在 `fixture.json` 上（29 组 / 41 节点），其中 44 条标了
  `requires: fixture`。换库、换领域仍未验证；真实库模式（`--db`）会跳过这些用例并**如实报数**
  （不静默少测）。
- **没有 embedding 基线**：缺「vs 向量检索」这一列，所以只能回答「为什么不用纯 BM25」。
- **硬负例暴露了真问题**：7 条负例只过 1 条（`14%`）。按原先的要求把负例改成「和已有节点共享
  常见词但主题不同」之后，两套系统都会自信地给出近邻 —— **这套设计分不清「我不知道」与
  「这是近邻」**。这是最值得改的一处：需要一个「低置信就说不确定」的判据，而不是永远返回最近的一条。
- **hybrid 慢得多**（这次读数 174ms vs 0.1ms）：它要跳图。这个规模下无所谓，规模上来要重新量。
- **过拟合风险**：用例是从同一个装置库反推出来的，调参时看着它们改很容易刷高。新增用例前，
  先确认它在**基线上真的失败**，否则只是重复计分。

## 怎么加用例

编辑 `cases.json`，然后跑一次。新增用例前先确认它在**基线上真的失败**，否则只是重复计分。
