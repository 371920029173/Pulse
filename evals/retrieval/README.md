# Retrieval evaluation / 检索评测

```
node evals/retrieval/run.mjs              # 默认用 fixture（无需真实库）
node evals/retrieval/run.mjs --db <path>  # 指定真实库（例如 <工作区>/.she/kb.sqlite）
node evals/retrieval/run.mjs --json       # 机器可读输出
```

**不调用任何 LLM API**，纯离线，毫秒级。

没有真实库时会自动退回 `fixture.json`：它是一份静态样本，复现检索的结构形态，让 CI 在没有
个人知识库的机器上也能跑。要评估真实数据就传 `--db`。

## 为什么要做这个

这个项目的核心主张是「用结构共振检索替代向量检索」。**主张在没有数字之前只是个人意见**，而任何读者第一个问题都是「为什么不直接用 BM25 / embedding？」

所以每个用例都**同时用两套系统跑同一份数据**：

| 列 | 是什么 |
|---|---|
| `hybrid` | `GroupKBEngine.query()` — 结构共振 + BM25 + 锚点 |
| `bm25` | `store.bm25Search()` — 纯词法，诚实的基线 |

**两列的差距就是证据。**

## 当前结果（真实库：12 组 / 27 节点）

```
Top-1 命中    hybrid 100% (15/15)    bm25 73% (11/15)
Top-3 召回    hybrid 100% (15/15)    bm25 73% (11/15)
负例（不该命中） 100% (1/1)
```

### 增益来自哪里（重要）

`+4` **全部来自组路径查询**。看用例表里那几行的「条数」列：

```
group-ops-env                hybrid ✓   bm25 ✗   条数 13/0
group-user-preferences       hybrid ✓   bm25 ✗   条数  8/2
group-user-passphrases       hybrid ✓   bm25 ✗   条数  8/2
group-name-only              hybrid ✓   bm25 ✗   条数 15/1
```

BM25 返回 0~2 条 —— 因为它索引**节点文本**，不索引**组名**。也就是说：

> 结构检索的价值不是「语义更准」，而是**能回答词法检索根本无法寻址的一类查询**。

这是个诚实、可检验、也不夸大的结论。语义类用例上两者打平（都 100%）——**这一点必须承认**，不能说结构检索在语义匹配上更强。

## 用例设计

`cases.json` 分四类：

| kind | 判据 |
|---|---|
| `group` | top-1 必须**属于**该组（不是标题匹配——早期版本拿标题去匹配组路径，永远匹配不上，得出过错误的 60%） |
| `title` | top-1 必须是**那条**节点 |
| `semantic` | top-1 属于可接受组集合中的任意一个（多个组合法地覆盖同一主题） |
| `negative` | 库中完全不存在的主题，**不应**给出命中 |

## 已知局限（别当它比实际更强）

- **用例只有 16 条**，规模小，不能当作统计上可靠的基准。
- **只在一个库上跑过**。换库、换语言、换领域未验证。
- **负例太弱**：`量子计算 硬件架构` 的词在库里一个都没有，两套系统都返回 0 条，等于白测。真正有意义的负例应该是「和已有节点共享常见词但主题不同」，目前没有。
- **没有 embedding 基线**。缺「vs 向量检索」这一列，所以无法回答「为什么不用 embedding」——只能回答「为什么不用纯 BM25」。
- 用例是从**同一个库**反推出来的，存在过拟合风险：调参时看着这些用例改，很容易刷高。

## 怎么加用例

编辑 `cases.json`，然后跑一次。新增用例前先确认它在**基线上真的失败**，否则只是重复计分。
