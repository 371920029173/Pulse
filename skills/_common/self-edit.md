# 改自己：安全编辑与自检（所有档通用）

> 这个工作区就是**我自己的代码**。所以"改功能"= 改我自己；
> 下面这些不是风格建议，是我这一轮真实踩过的坑写成的硬规则。

## 1. 改源码只用这三步

```bash
# ① 锚点与替换内容都写成文件（绝不把代码写进命令行）
node scripts/patch.mjs --file <目标> --from a.txt --to b.txt            # dry-run
node scripts/patch.mjs --file <目标> --from a.txt --to b.txt --apply    # 写盘并回读确认
```

为什么：`node -e "…模板串…"` 经过 cmd.exe 时，`\``、`${}`、`'` 会被吃掉 —— 这一轮我因此
**改坏过 4 次**（一次把 system-prompt.ts 的模板串截断、两次把 langs.ts 写坏）。
`scripts/patch.mjs` 强制三件事：锚点必须**恰好命中 1 次**；命中 0 次就**整批不写**；
写回后**回读校验**，不一致自动恢复原文件。

## 2. 每次改完，立刻自证

- 改 TS：`pnpm --filter <包> build`（类型错当场红）；
- 改行为：跑该包的单测；改动涉及门禁链再跑对应 `check:*`；
- **改完先 grep 一次自己的标记**（新加的注释/函数名），确认它真的在文件里 ——
  这一轮我有两次"以为改了、其实脚本静默没写"。

## 3. 说"可以了"之前，先问是哪一层

同一件事有三层证据，**不能拿一层的结论去答另一层**：

| 层 | 证据 | 反例（我犯过） |
|---|---|---|
数据层 | `map:query verify` 的边数/标签数 | 63 条接线 → 我说"AGI 那边可以了" |
入口层 | 那个工作区有没有 skill、工具表里有没有工具 | skill 目录根本不存在 |
行为层 | 模型真的调用它、真的拿到结果 | 完全没验 |

## 4. 长程任务的停法

- 有计划就继续做，**一步一 `plan_update`**；不要用"看起来没进展"当停止理由（门限已删）；
- 真正该停的只有三种：做完了、撞到轮数/预算、或者需要只有用户知道的信息。

## 5. 派活与等待

- 宽而杂、不需要逐步判断的活才 `task_spawn({ background: true })`；
- 回来 `task_status({ ids, wait: true })` 收 Ergebnis；等 shell 任务用 `shell_wait({ ids, mode })`；
- **不要轮询**：本仓明确禁止 poll；工具里已经提供了"等什么结束"的能力。

## 6. 报告要分"已做/未做"

- 未验证的不写成"完成"；有已知缺口就写进"已知缺口"一节（如手册 §9 的 C#）；
- 跑门禁时如果日志中途断掉（进程崩了），**那是没有结论**，不是通过 —— 重跑。
